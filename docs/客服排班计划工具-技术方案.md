# 客服排班计划工具 · 技术方案

> 文档版本：1.0  
> 编制日期：2026-09-25  
> 需求依据：[PRD 修订版](./客服排班计划工具-PRD-修订版.md) 与 [版本迭代与升级方案修订版](./客服排班计划工具-版本迭代与升级方案-修订版.md)

## 1. 方案结论

采用“Electron 桌面壳 + TypeScript 领域层 + 随包携带的 OR-Tools CP-SAT 求解器 + ExcelJS + 版本化 JSON 文件库”的离线架构。

```text
React/TypeScript 界面
        │ 受限、类型化 IPC
Electron 主进程
 ├── 领域校验器（TypeScript 纯函数）
 ├── 本地数据仓储与迁移
 ├── Excel 导入/导出服务
 ├── 文件选择、备份、恢复、日志
 └── 求解器编排器 ── JSON stdin/stdout ── scheduler-solver.exe
                                              └── Python + OR-Tools CP-SAT
```

这套拆分满足四个关键约束：

- 用户电脑只运行一个绿色版 EXE，不需安装 Node、Python、Office 或数据库；
- 浏览器界面不直接读写文件、不直接调用求解器；
- 排班算法能够严格表达硬约束，并对软约束分层优化；
- 配置、排班历史和备份可离线迁移、原子恢复、长期追溯。

## 2. 技术选型

| 层级 | 选型 | 职责与理由 |
| --- | --- | --- |
| 桌面运行时 | Electron | 与 PRD 的 Windows 自包含交付一致；负责窗口、受控 IPC、文件选择和进程管理 |
| 用户界面 | React + TypeScript | 适合密集表格、配置表单与状态面板；严格类型降低规则配置出错率 |
| 领域层 | TypeScript 纯函数 | 数据 schema、预检查、结果校验、统计、评分、迁移和导出数据准备可脱离 UI 单测 |
| 排班求解 | Google OR-Tools CP-SAT | 适合“员工 × 日期 × 状态”的布尔约束模型，能够同时处理可行性与目标优化 |
| 求解器交付 | 打包为 `scheduler-solver.exe` 的 Python 侧车 | 开发期使用 Python OR-Tools；发布期把解释器和依赖一并封装，目标机无 Python 依赖 |
| Excel | ExcelJS | 读取导入模板、写入样式及公式；导出时由程序提供公式缓存结果 |
| 数据存储 | 版本化 JSON 文件库 | 数据量小、人工可审计、备份直观；天然匹配 schemaVersion、快照、排班版本与原子文件替换 |
| 测试 | 单元测试 + 求解器集成测试 + 黄金文件比对 + 桌面端端到端测试 | 覆盖规则正确性、导出格式、迁移恢复和关键交互 |

不采用纯前端或纯 TypeScript 的自研贪心排班器作为核心求解器：它难以保证 H1～H9 同时满足，也无法可靠区分“无解”与“搜索不够好”。CP-SAT 对排班中的“唯一状态、最低覆盖、人员技能、锁定日期、休息总数”等约束有直接表达能力。[OR-Tools 排班示例](https://developers.google.com/optimization/scheduling/employee_scheduling)

## 3. 总体架构

### 3.1 进程边界

| 进程/模块 | 可以做什么 | 不可以做什么 |
| --- | --- | --- |
| 渲染进程 | 展示页面、编辑草稿、调用受限 API、呈现校验结果 | 直接访问文件系统、执行命令、读取完整 IPC 能力 |
| preload | 暴露最小化的类型化 `window.scheduler` API | 向页面暴露 `ipcRenderer` 或 Node API |
| 主进程 | 校验 IPC、管理文件、保存数据、启动/取消求解器、导入导出 | 承载复杂的表格视图和规则展示逻辑 |
| 求解器侧车 | 接收标准化 JSON、构建模型、返回结果和指标 | 访问任意用户目录、直接修改业务数据 |

Electron 窗口必须保持 `contextIsolation: true`、`nodeIntegration: false`。preload 仅通过 `contextBridge` 暴露白名单方法，主进程逐条校验 IPC 发送方和参数；不得把整个 `ipcRenderer` 直接暴露给界面。[Electron 安全与 IPC 指引](https://www.electronjs.org/docs/latest/tutorial/security)

### 3.2 建议代码目录

```text
customer-service-scheduling/
├── apps/
│   ├── desktop/
│   │   ├── main/                 # Electron 主进程、IPC、文件和生命周期
│   │   ├── preload/              # 最小化桥接 API
│   │   └── renderer/             # React 页面、表格和交互
│   └── solver/
│       ├── src/                  # Python CP-SAT 模型和 JSON 协议
│       └── build/                # 打包得到的 scheduler-solver.exe
├── packages/
│   ├── contracts/                # JSON schema、DTO、错误码、IPC 类型
│   ├── domain/                   # 预检查、校验、统计、评分、边界状态
│   ├── persistence/              # 仓储、原子写入、备份、迁移
│   └── excel/                    # 模板解析、导出和黄金文件比对
├── fixtures/                     # 可发布/有例外/不可行/跨月样例
├── templates/                    # 版本化 Excel 模板与 layout manifest
├── tests/
│   ├── unit/
│   ├── integration/
│   ├── migration/
│   └── e2e/
└── docs/
```

`contracts` 是桌面端、领域层与求解器之间唯一的数据协议来源。任何字段新增、删除或语义变化，必须先调整 schemaVersion、迁移函数和测试样例，不能只改界面。

## 4. 核心数据与本地存储

### 4.1 文件库布局

配置和历史记录属于小型业务数据，保存在 Electron 的应用数据目录下的产品专属子目录；用户导出的 Excel/CSV 保存在用户选择的位置，不纳入自动备份。

```text
<userData>/customer-service-scheduling/
├── manifest.json                 # 当前 schema、活动版本、事务和校验摘要
├── current/
│   └── configuration.json         # 当前生效配置
├── snapshots/
│   └── <snapshotId>.json
├── schedules/
│   └── 2026-10/<scheduleId>.json
├── boundaries/
│   └── 2026-09.json               # 下月需要的月末边界状态
├── backups/
│   └── <timestamp>-<schemaVersion>/
├── transactions/
│   └── <transactionId>/
├── logs/
└── lock/
```

每份 `scheduleRecord` 保存：目标月份、结果状态、配置快照 ID、边界状态 ID、`solverVersion`、随机种子、软约束得分、人工修改日志、导出记录和结果校验摘要。

### 4.2 原子保存与恢复

所有写操作遵循同一事务：

1. 获取单实例写入锁；
2. 在 `transactions/<id>` 写入完整的新文件；
3. 校验 JSON schema、引用完整性、记录数量和 SHA-256；
4. 生成保护性备份（迁移、导入覆盖、恢复和重置时必做）；
5. 通过同一数据卷内的原子重命名切换 `manifest.json` 指向的新版本；
6. 写入操作日志后释放锁。

下次启动检测到未完成事务时，不继续覆盖，而是验证并恢复到最近一个完整清单。排班历史采用追加式版本文件；重新生成和人工调整创建新版本，不修改旧版本。

### 4.3 核心协议对象

```ts
type AssignmentState = 'OFF' | PositionId;

interface ScheduleRequest {
  requestId: string;
  schemaVersion: number;
  solverVersion: string;
  targetMonth: 'YYYY-MM';
  configuration: ConfigurationSnapshot;
  boundaryState?: BoundaryState;
  lockedAssignments: LockedAssignment[];
  mode: 'PUBLISHABLE' | 'EXCEPTION';
  timeLimitSeconds: number;
  randomSeed: number;
}

interface ValidationIssue {
  code: string;
  ruleId?: 'H1' | 'H2' | 'H3' | 'H4' | 'H5' | 'H6' | 'H7' | 'H8' | 'H9' | 'S1' | 'S2' | 'S3' | 'S4' | 'S5';
  severity: 'ERROR' | 'WARNING' | 'INFO';
  employeeId?: string;
  date?: string;
  expected?: string | number;
  actual?: string | number;
  sourceIds: string[];
  messageKey: string;
}
```

所有人员、岗位、规则、快照和排班记录只通过 UUID 关联；姓名与岗位名称是可变展示属性。导入时优先以员工编号匹配，重复姓名但没有员工编号时阻止静默导入。

## 5. 排班算法设计

### 5.1 求解变量

对于员工 `e`、日期 `d`、状态 `s` 创建布尔变量：

```text
x[e, d, s] = 1  表示员工 e 在日期 d 处于状态 s
s ∈ {OFF, 早, 中, 审单, 后台, ...配置的全部岗位}
```

员工不具备岗位技能时，不创建该岗位变量或强制其值为 0。这样不会出现无技能顶岗。

### 5.2 硬约束映射

| PRD 规则 | CP-SAT 表达 |
| --- | --- |
| H1 每日唯一状态 | `Σs x[e,d,s] = 1` |
| H2 岗位最低配额 | `Σe x[e,d,p] ≥ quota[d,p]`；无技能变量为 0 |
| H3 精确月休 | `Σd x[e,d,OFF] = restDays[e]` |
| H4 三人组 | 对每组、每天：`Σe∈group x[e,d,OFF] ≤ 1` |
| H5 互斥对 | 对每对、每天：`x[a,d,OFF] + x[b,d,OFF] ≤ 1` |
| H6 指定休息 | `x[e,d,OFF] = 1` |
| H7 指定岗位 | `x[e,d,p] = 1` |
| H8 指定休息人数 | `Σe x[e,d,OFF] = specifiedRestCount[d]` |
| H9 指定审单 | `x[e,d,审单] = 1`，并在预检查验证审单技能 |

“岗位最低配额”意味着满足配额后允许多安排人员至其具备技能的岗位；不再使用弹性日或无归属的机动状态。

### 5.3 跨月边界

`BoundaryState` 只保存计算所需的上月末事实，不复制整月无关数据：

- 目标月首周前的同一自然周排班状态；
- 每名员工月末连续上班天数和连续休息天数；
- 用于倒班判断的最近岗位序列；
- 来源排班记录 ID、来源月份和完整性标记。

生成当前月时，边界状态作为常量参与 S1、S3、S4、S5 的计算。生成完成后写出新的月末边界。若上月数据缺失且用户确认降级，则返回 `CROSS_MONTH_NOT_FULLY_VERIFIED` 警告；该警告不会伪装成已完整校验。

### 5.4 分层目标优化

先寻找硬约束可行解，再按软约束层级顺序多次求解：

1. 固定所有硬约束，寻找可行解；
2. 最小化用户勾选的最高优先级软约束的标准化违规分；
3. 固定该层最优分值，继续最小化其余默认层级；
4. 返回每层分数、总分、求解状态、耗时和随机种子。

该词典序策略比“把所有权重相加为一个大数”更稳定，也能真实兑现“最高优先级先满足”的产品语义。

软约束指标建议如下：

| 规则 | 违规度量 |
| --- | --- |
| S1 倒班规避 | 相邻工作日岗位切换次数；可对“早↔中”设置更高惩罚 |
| S2 中班均匀 | `max(中班数) - min(中班数)` 超过 3 的差值 |
| S3 连休段 | 每人连续 2 天休息段数量与目标区间 [1,2] 的距离 |
| S4 休中休 | 两个休息段间连续上班长度落在 [3,6] 外的距离 |
| S5 每周上班 | 完整自然周上班天数落在 [3,6] 外的距离；6 上 1 休作为较低偏好 |

### 5.5 无解与有例外方案

预检查失败（引用断裂、指定冲突、无技能锁定等）时，不调用求解器，直接返回“无可行方案”。

预检查通过但标准模型无解时，才启动第二个“有例外”模型：为可放宽的硬约束建立违规变量，并按违规严重度词典序最小化。返回的每个违规必须能映射到 `ValidationIssue`。锁定冲突、数据结构错误和无技能安排不允许在有例外模式下被静默放宽。

### 5.6 人工调整与智能调班

- **强制修改**：更新草稿排班后立即执行 TypeScript 校验器；出现硬约束违规时将结果标为“有例外”。
- **智能调班**：把目标员工、日期、期望状态和当前排班作为新锁定/提示输入，目标函数首层最小化“与当前排班不同的单元格数”，再优化软约束。返回 1～3 个调整建议供用户确认。
- **候选方案（P1）**：为每个已选方案增加最小汉明距离约束，保证新方案与已选方案至少有指定数量的单元格不同。

### 5.7 性能与取消

- 轻量预检查和单表校验在主进程工作线程中执行，基准数据 P95 小于 300ms；
- 正式求解在侧车进程执行，默认 3 秒时限；
- 主进程将进度、最优界和取消信号转发给界面；
- 取消时先请求侧车停止，超出短暂宽限后终止子进程，并把草稿保持为未发布状态；
- 求解超时但存在可行解时返回“可发布候选（未证明最优）”；没有可行解时明确返回超时，不得误报无解。

## 6. 领域校验器与预检查

领域校验器以 TypeScript 纯函数实现，既用于导入、表单编辑和人工调整，也用于对求解器输出进行二次校验。它不负责搜索解，但必须独立确认返回排班满足 H1～H9。

预检查分三层：

| 层级 | 示例 | 行为 |
| --- | --- | --- |
| 结构校验 | 缺少必填字段、非法日期、UUID 不存在 | 阻止保存和生成 |
| 业务必然冲突 | 同日既指定休息又指定审单、锁定岗位无技能 | 阻止生成并定位来源 |
| 容量风险 | 每日最低配额超过在职人数、技能人数不足 | 阻止生成；显示岗位、日期与缺口 |

求解器输出必须经过领域校验器；若两者结果不一致，保留输入/输出至诊断目录、禁止发布并记录高优先级错误。

## 7. Excel 导入导出

### 7.1 模板策略

每个模板包含 `templateVersion` 和配套的 `layout-manifest.json`。manifest 显式定义 Sheet 名、表头、数据开始行、映射列、统计单元格、冻结窗格、合并区域、打印区域和样式标识。程序不得依赖“第 3 个 Sheet、第 5 列”这类隐式约定。

导入服务流程：

```text
选择文件 → 只读取工作簿数据 → 解析为导入 DTO → schema 校验
→ 稳定 ID 匹配/消歧 → 业务预检查 → 预览差异 → 创建快照
```

导入仅把单元格当作数据，不执行宏、外部链接或工作簿内公式。

### 7.2 Excel 导出

导出服务按黄金样例创建工作簿，并从领域统计函数获得所有统计值。ExcelJS 支持写入“公式 + 缓存结果”，但不会自行计算公式，因此程序必须写入两者；公式使用英文函数名与逗号分隔符。[ExcelJS 公式模型说明](https://github.com/exceljs/exceljs#formula-value)

```ts
cell.value = {
  formula: 'COUNTIF(B2:AF2,"休")',
  result: calculatedRestDays,
};
```

导出验收分两类：

- **内容比对**：员工、日期、岗位、统计、结果状态与领域数据一致；
- **布局比对**：与黄金样例比对 Sheet、单元格位置、样式、公式、冻结窗格、合并单元格和打印区域。

CSV 只导出排班明细值，固定 UTF-8 with BOM；有例外方案追加结果状态和确认原因列。

## 8. 安全、隐私与可靠性

### 8.1 安全边界

- 只加载本地打包资源，设置严格 Content Security Policy；
- 所有 IPC 采用明确的命令和 DTO；主进程验证发送方、schema 和文件扩展名；
- 文件选择必须由主进程弹窗发起；界面不能任意传入系统路径；
- 求解器仅接收 JSON 标准输入、只输出 JSON 标准输出，禁止继承不必要的环境变量或文件访问权限；
- 异常日志记录错误码、版本和事务 ID，姓名、完整排班及原始 Excel 内容默认脱敏或不记录。

### 8.2 可靠性机制

- 单实例锁防止两个程序同时写同一数据目录；
- 所有备份带清单和校验和；
- 迁移、导入覆盖、恢复、重置均先创建保护性备份；
- 历史排班与配置快照不可原地覆盖；
- 旧版遇到高 schema 只读保护，恢复前不允许写入；
- 侧车崩溃、求解超时和导出失败不改变已保存的正式排班。

## 9. 测试方案

### 9.1 测试资产

沿用 PRD 的四类数据集，并为每条 H/S 规则增加正例、反例与边界例：

1. 存在可发布解；
2. 仅软约束无法完全满足；
3. 硬约束不可行；
4. 含上月边界状态的跨月样例。

### 9.2 自动化测试矩阵

| 范围 | 关键断言 |
| --- | --- |
| 领域单元测试 | H1～H9、S1～S5、跨月边界、问题定位、统计与评分 |
| 求解器集成测试 | 合法解、无解、有例外、超时、取消、随机种子可复现 |
| 导入导出测试 | 模板版本、字段错误定位、黄金 Excel、CSV BOM 与公式缓存值 |
| 数据迁移测试 | 每一 schema 跳迁、重复迁移、失败恢复、旧版只读保护 |
| 桌面端端到端测试 | 初始化、导入、生成、强制修改、智能调班、导出、恢复 |
| 打包冒烟测试 | 干净 Windows 10/11 x64 环境无需外部运行时启动 |

任何一次发布均须执行：从最低兼容 schema 逐级升级、恢复到升级前备份、导入旧模板、导出黄金样例、运行四类排班数据集。

| 2. 数据底座 | JSON 仓储、快照、锁、事务、备份和 `schemaVersion=1` | 中断写入后能恢复，历史不丢失 |
| 3. 预检查与校验 | H1～H9 校验器、导入 DTO、问题面板数据 | 三类样例的预检查结果符合预期 |
| 4. 求解器 POC | CP-SAT 可发布解、跨月边界、超时和取消 | 基准数据生成 P95 小于 3 秒 |
| 5. 排班闭环 | 月视图、生成、强制修改、智能调班、结果状态 | 能完成“配置→生成→调整→保存” |
| 6. Excel 闭环 | 模板下载、导入预览、Excel/CSV 导出、黄金比对 | 模板验收全部通过 |
| 7. 升级交付 | 迁移、恢复页面、升级包、绿色版测试 | 升级/降级/失败恢复测试通过 |

AI 开发时必须遵守以下约束：

- 先改 `contracts`、样例和测试，再改实现；
- 禁止在 React 组件中写排班规则；
- 禁止让求解器直接读写业务数据目录；
- 任何 schema 变化必须附迁移函数、备份测试和兼容矩阵更新；
- 任何导出格式变化必须更新 `templateVersion` 与黄金样例；
- 任何已保存历史排班不得被新算法静默覆盖或重算。

## 11. 首个可开发版本的边界

首版应只交付 P0 的单机闭环：配置、预检查、生成、三种状态、跨月边界、强制修改、智能调班、历史、Excel/CSV 和备份恢复。多候选方案、统计面板、岗位筛选导出和便携模式依照 PRD 保持 P1，不阻塞首版上线。

在启动编码前，唯一需要补齐的业务资产是：真实匿名化人员/技能/规则样例、当前 Excel 模板原件，以及主管对“有例外方案”可放宽规则的授权清单。其余内容可按本方案直接拆分为 AI 编程任务。
